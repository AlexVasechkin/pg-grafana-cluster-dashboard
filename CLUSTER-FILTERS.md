# Фильтры дашборда «Состояние кластера»

Описание переменных (template variables) Grafana для `pg-cluster.json` и требований
к конфигурации скрейпа, которые эти фильтры обеспечивают.

Уровни привязки метрик (**У / Б~ / Б= / К / У+**) — см. `CLUSTER-METRICS.md` §1.
Все запросы ниже проверены на VictoriaMetrics v1.103.0 с четырьмя таргетами
(Patroni-кластер из 3 узлов, один из них недоступен, + standalone).

---

## 1. Состав фильтров

| № | Переменная | Тип | Зависит от | Выбор | Назначение |
|:-:|---|---|---|---|---|
| 1 | `$pg_cluster` | query | — | **один** | какой кластер (или standalone-сервер) смотрим |
| 2 | `$node` | query | `$pg_cluster` | **только один** | узел для панелей уровня У / У+ |
| 3 | `$db_name` | query | `$pg_cluster` | мульти + `All` | база для панелей уровня Б= / Б~ |

Каскад: `pg_cluster → node`, `pg_cluster → db_name`. **`db_name` зависит от кластера,
а не от узла** — список БД реплицируется и на всех узлах одинаков (уровень Б=,
проверено в `CLUSTER-METRICS.md` §1), поэтому привязывать его к `$node` бессмысленно
и только мешало бы: при смене узла список бы перестраивался без причины.

## 2. Фильтр 1 — `$pg_cluster`

```json
{
  "name": "pg_cluster",
  "label": "Кластер",
  "type": "query",
  "datasource": { "type": "prometheus", "uid": "victoriametrics" },
  "definition": "label_values(up{job=\"postgres\"}, pg_cluster)",
  "query": "label_values(up{job=\"postgres\"}, pg_cluster)",
  "multi": false,
  "includeAll": false,
  "refresh": 2,
  "sort": 1,
  "hide": 0
}
```

- `refresh: 2` — «On Time Range Change»: новый кластер появляется в списке без
  перезагрузки дашборда.
- `sort: 1` — алфавитный порядок.
- `multi: false` — **осознанное решение**, см. §6.

### Почему якорь именно `up`, а не `pgcls_*` и не `pg_up`

Это главный нюанс конфигурации фильтров, проверен экспериментально.

| Якорь | Что вернул фильтр `node` для `pg-cluster` | Недоступный узел pg3 |
|---|---|---|
| `up` (генерит скрейпер VM) | `['pg1', 'pg2', 'pg3']` | **виден** |
| `pg_up` (генерит экспортёр) | `['pg1', 'pg2']` | **пропал** |

`up` — метрика самого скрейпера, она есть у таргета всегда, даже если экспортёр не
отвечает (`up=0`). `pg_up` экспортёр отдаёт только когда сам жив, а `pgcls_*` — только
когда жив и смог выполнить SQL.

> ⚠️ Если опереть фильтры на `pgcls_*` или `pg_up`, **упавший узел исчезнет из
> выпадающего списка** — именно тогда, когда его нужно выбрать и посмотреть, что
> случилось. Якорем для `$pg_cluster` и `$node` берём только `up`.

Проверено: `pg_up` отдаётся **несмотря на** `PG_EXPORTER_DISABLE_DEFAULT_METRICS=true`
(как и `pg_locks_count`, `pg_replication_lag_seconds`, `pg_replication_is_replica`,
`pg_database_size_bytes` — встроенные коллекторы остаются включёнными). Но для
фильтров это всё равно не годится по причине выше.

Фильтр `job="postgres"` в якоре — чтобы в список не попали кластеры, у которых есть
только таргет `patroni` или `node_exporter` (см. `CLUSTER-METRICS.md` §6), но ещё нет
postgres-экспортёра. Если хотите видеть такие кластеры тоже — уберите фильтр `job`.

## 3. Фильтр 2 — `$node` (только один узел)

```json
{
  "name": "node",
  "label": "Узел",
  "type": "query",
  "datasource": { "type": "prometheus", "uid": "victoriametrics" },
  "definition": "label_values(up{job=\"postgres\", pg_cluster=\"$pg_cluster\"}, node)",
  "query": "label_values(up{job=\"postgres\", pg_cluster=\"$pg_cluster\"}, node)",
  "multi": false,
  "includeAll": false,
  "refresh": 2,
  "sort": 1,
  "hide": 0
}
```

`multi: false` + `includeAll: false` — ровно одна нода, как в постановке. Это даёт
`$node` всегда скалярное значение, поэтому в панелях можно писать `node="$node"`
без регекс-формы `node=~"$node"`.

Проверено на живом VM:

| Выбран кластер | `label_values(up{pg_cluster="…"}, node)` |
|---|---|
| `pg-cluster` | `['pg1', 'pg2', 'pg3']` |
| `srv-db-01` (standalone) | `['srv-db-01']` |

### Важно: не все панели должны использовать `$node`

Раз `$node` одиночный, панели, которые **сравнивают узлы между собой**, обязаны его
игнорировать и фильтроваться только по `$pg_cluster`. Иначе от «светофора кластера»
останется одна строка.

| Панели | Фильтр в запросе |
|---|---|
| Светофор кластера, таблица узлов, lag по всем репликам, расхождения конфига, «лидеров = 1» | **только** `{pg_cluster="$pg_cluster"}` |
| Детализация узла: его WAL, checkpoint, слоты, соединения, wait-events, прогресс операций | `{pg_cluster="$pg_cluster", node="$node"}` |
| Б=-панели (размеры, wraparound) | `{pg_cluster="$pg_cluster"}` + `max by (pg_cluster, db_name)` |
| Б~-панели (TPS, cache hit, deadlocks) | либо `node="$node"`, либо джойн с `is_primary` (см. §5) |

Рекомендация по компоновке: секции 1–4 дашборда (обзор, репликация, слоты/WAL,
предаварийное) — **на уровне кластера**, без `$node`; секции 6–8 (checkpoint/IO,
конфигурация, операции) — **с `$node`**, и в заголовки таких панелей подставлять
`($node)`, как уже сделано в `pg-tables.json` с `($table)`.

В собранном дашборде из этого правила есть одно исключение — секция 0 «Сводка»: там
соседствуют кластерные панели (нагрузка, блокировки по режимам) и панель соединений
**с `node="$node"`**. Соединения принципиально привязаны к узлу: у лидера это пишущие
приложения и walsender'ы, у реплики — читатели и walreceiver; агрегат по кластеру
смешал бы два профиля. Признак такой панели — `($node)` в заголовке.

### Значение по умолчанию

При переключении кластера Grafana проверяет, есть ли текущее значение `$node` в новом
списке; если нет — берёт первое. Переход `pg-cluster → srv-db-01` подставит
`srv-db-01` сам. Чтобы по умолчанию попадать на лидера, а не на `pg1` по алфавиту,
дашборд можно открывать ссылкой с `?var-node=…`, либо добавить отдельную панель-таблицу
«кто лидер» со ссылкой-дриллдауном (data link `?var-node=${__data.fields.node}`).

## 4. Фильтр 3 — `$db_name`

```json
{
  "name": "db_name",
  "label": "База",
  "type": "query",
  "datasource": { "type": "prometheus", "uid": "victoriametrics" },
  "definition": "label_values(pgcls_db_size_bytes{pg_cluster=\"$pg_cluster\"}, db_name)",
  "query": "label_values(pgcls_db_size_bytes{pg_cluster=\"$pg_cluster\"}, db_name)",
  "multi": true,
  "includeAll": true,
  "allValue": ".*",
  "refresh": 2,
  "sort": 1,
  "hide": 0
}
```

- Якорь — **Б=-метрика** (`pgcls_db_size_bytes` или `pgcls_db_xid_age`): она есть для
  каждой БД и по смыслу привязана к кластеру, а не к узлу. `up` здесь не подходит —
  у него нет метки `db_name`.
- `multi: true` + `includeAll: true` — панели «по всем БД» (wraparound, размеры) это
  основной режим; `All` разворачивается в `.*` и подставляется как `db_name=~"$db_name"`.

**Дедупликация работает сама.** Б=-метрика собирается со всех узлов, то есть серий у
неё N (по числу узлов), но `label_values` возвращает уникальные значения. Проверено:

```
pgcls_db_size_bytes{pg_cluster="pg-cluster"}   →  3 серии:
    {node="pg1", db_name="shop"}  {node="pg2", db_name="shop"}  {node="pg1", db_name="billing"}
label_values(pgcls_db_size_bytes{pg_cluster="pg-cluster"}, db_name)
                                               →  ['billing', 'shop']   # shop один раз, не два
```

Проверено через прокси самой Grafana (`/api/datasources/proxy/uid/victoriametrics`),
то есть ровно тем путём, которым переменную резолвит дашборд.

В самих панелях дубли так не схлопнутся — там нужен `max by (pg_cluster, db_name)`
(см. `CLUSTER-METRICS.md` §1).

## 5. Вспомогательные переменные (опционально)

| Переменная | Тип | Зачем |
|---|---|---|
| `$ds` | datasource (`prometheus`) | если VM несколько (по ЦОД/контуру) — иначе uid `victoriametrics` прошит в панелях |
| `$leader` | query, `hide: 2` (скрытая) | `query_result(pgcls_node_is_primary{pg_cluster="$pg_cluster"} == 1)` + regex-выделение `node` — чтобы Б~-панели можно было фильтровать лидером без джойна |
| `$ha` | custom / query, `hide: 2` | `patroni` / `none` — скрывать секцию репликации на standalone (см. §6.3) |

Если скрытый `$leader` делать не хочется, Б~-метрики берутся с лидера джойном —
вариант надёжнее, он не зависит от порядка обновления переменных:

```promql
sum by (pg_cluster, db_name) (
  rate(pgcls_db_xact_commit{pg_cluster="$pg_cluster"}[$__rate_interval])
  and on(pg_cluster, node) (pgcls_node_is_primary == 1)
)
```

> ⚠️ Именно `and on(...)`, а не `* on(...) group_left pgcls_node_is_primary`. Проверено
> на живом VM: умножение на флаг **не отбрасывает** серии реплик, а присваивает им 0
> (3 серии вместо 2). Под `sum by` сумма получается верной, но любая неагрегированная
> панель нарисует плоские нули по каждой реплике.

## 6. Конфигурация скрейпа: Patroni и standalone в одном дашборде

### 6.1. Соглашение по меткам

Дашборд работает с любым из двух видов целей, если соблюдать правило:

| Вид цели | `pg_cluster` | `node` | Пример |
|---|---|---|---|
| Patroni-кластер | имя кластера (Patroni `scope`) | имя узла | `pg_cluster: pg-cluster`, `node: pg1` |
| **Standalone без Patroni** | **= `node`** (имя сервера) | имя сервера | `pg_cluster: srv-db-01`, `node: srv-db-01` |

```yaml
scrape_configs:
  - job_name: postgres
    static_configs:
      # --- Patroni-кластер: pg_cluster != node ---
      - targets: ["pg1-exporter:9187"]
        labels: { pg_cluster: pg-cluster, node: pg1, ha: patroni }
      - targets: ["pg2-exporter:9187"]
        labels: { pg_cluster: pg-cluster, node: pg2, ha: patroni }
      - targets: ["pg3-exporter:9187"]
        labels: { pg_cluster: pg-cluster, node: pg3, ha: patroni }

      # --- Standalone: pg_cluster == node ---
      - targets: ["srv-db-01:9187"]
        labels: { pg_cluster: srv-db-01, node: srv-db-01, ha: none }
      - targets: ["srv-db-02:9187"]
        labels: { pg_cluster: srv-db-02, node: srv-db-02, ha: none }
```

На стенде это сделано для контейнера `subscriber` (standalone-подписчик логической
репликации): `pg_cluster: subscriber, node: subscriber, ha: none`. Проверено, что
соглашение работает именно так, как здесь описано: в фильтре «Кластер / сервер» два
значения (`pg-cluster`, `subscriber`), а каскад по `subscriber` даёт ровно один узел.
Заодно подтвердился выбор якоря `up`: PostgreSQL в контейнере ещё не поднят, и при
якоре `pg_up` или `pgcls_*` сервер в списке бы **не появился** вовсе (`up=1`,
`pg_up=0`).

Проверено на живом VM с ровно такой смесью целей:

- `label_values(up{job="postgres"}, pg_cluster)` → `['pg-cluster', 'srv-db-01']` —
  оба вида в одном списке;
- `label_values(up{pg_cluster="srv-db-01"}, node)` → `['srv-db-01']` — у standalone
  каскад даёт **ровно один** узел, так что требование «только одна нода» для него
  выполняется автоматически, а фильтр `$node` становится формальным;
- `label_values(up{pg_cluster="pg-cluster"}, node)` → `['pg1','pg2','pg3']`.

### 6.2. Что это даёт и чего стоит

Плюсы соглашения `pg_cluster = node`:

- одна и та же схема меток, один дашборд, один `queries.yaml` — без ветвлений;
- «К»-проверки остаются осмысленными: у здорового standalone
  `count(pgcls_node_is_primary == 1) by (pg_cluster)` = 1, ровно как у здорового
  Patroni-кластера. Ноль так же означает «primary нет» (сервер в recovery или лежит);
- фильтр 1 работает как общий список «что мониторим», независимо от вида цели.

Цена: **в терминах PostgreSQL «cluster» — это инстанс**, а здесь метка `pg_cluster`
означает HA-группу. Для standalone два понятия совпадают, и это как раз делает
соглашение непротиворечивым, но в подписях на дашборде лучше писать «Кластер / сервер»,
чтобы не путать DBA.

### 6.3. Пустые панели на standalone — это норма, но её надо отличать от аварии

У standalone нет реплик, поэтому `pgcls_repl_*` панели будут пустыми. Проблема в том,
что «реплик нет, потому что их и не должно быть» внешне не отличается от «кластер
потерял все реплики». Два варианта, как развести:

1. **Метка `ha` в скрейп-конфиге** (как в примере выше) + скрытая переменная `$ha`:
   секцию «Репликация» завести в row с `repeat`/условием по `$ha`, либо просто
   показывать в светофоре ожидаемое число реплик.
2. **Метка `expected_standbys`** (`0` для standalone, `2` для трёхузлового кластера) —
   тогда алерт пишется как
   `pgcls_repl_standby_count < on(pg_cluster) group_left max by (pg_cluster) (expected_standbys)`
   и одинаково корректен для обоих видов целей.

Без одного из этих способов алерт «реплика отвалилась» будет срабатывать на каждом
standalone-сервере. Рекомендую вариант 1 как более простой, вариант 2 — если
standalone много и нужны алерты, а не только дашборд.

Аналогично на standalone будут пустыми панели из `CLUSTER-METRICS.md` §6 (Patroni
`/metrics`, etcd) — для таких целей эти job'ы просто не создаются.

## 7. Сводка: какой фильтр к какому уровню метрик

| Уровень | Метки метрики | Фильтры в запросе панели |
|:--:|---|---|
| **К** | `{pg_cluster}` | `$pg_cluster` |
| **У** | `{pg_cluster, node}` | `$pg_cluster` (сравнение узлов) **или** `$pg_cluster` + `$node` (детализация) |
| **У+** | `{pg_cluster, node, <объект>}` | `$pg_cluster` + `$node`; для слотов — лучше без `$node`, чтобы видеть забытые слоты на всех узлах |
| **Б=** | `{pg_cluster, db_name}` | `$pg_cluster` + `$db_name`, с `max by (pg_cluster, db_name)` |
| **Б~** | `{pg_cluster, node, db_name}` | `$pg_cluster` + `$db_name` + (`$node` **или** `and on(pg_cluster, node) (pgcls_node_is_primary == 1)`) |

> Исключение по слотам стоит выделить: слоты **не реплицируются** (проверено,
> `CLUSTER-METRICS.md` §1 — на pg3 висели свои слоты от прошлой роли), поэтому таблицу
> слотов правильнее строить по всему кластеру, игнорируя `$node`, иначе забытый слот
> на неактивном узле не будет виден, пока его специально не выберут.

## 8. Открытый вопрос: один кластер или парк сразу

Фильтр 1 сделан одиночным (`multi: false`) — иначе `$node` и `$db_name` становятся
неоднозначными: «одна нода» из нескольких кластеров не определена. Это следует из
постановки (каскад + одиночная нода) и даёт дашборд-дриллдаун «выбрал кластер →
выбрал узел».

Побочный эффект: **обзор всего парка кластеров на этом дашборде недоступен**. Варианты:

| Вариант | Как | Когда выбирать |
|---|---|---|
| **A. Панель-исключение** (рекомендую) | в секции 1 одна таблица-светофор с запросом **без** `$pg_cluster` — все кластеры сразу, с data link на этот же дашборд с `?var-pg_cluster=…` | кластеров немного; хочется один дашборд |
| **B. Отдельный дашборд** `pg-fleet.json` | только К-метрики по всем кластерам, дриллдаун ссылкой | кластеров много (> 10) |
| **C. `multi: true` + row repeat** | `repeat` строк по `$pg_cluster`; `$node`/`$db_name` придётся убрать или тоже сделать мульти | нужен именно параллельный просмотр, детализацией по узлу готовы пожертвовать |

Нужно решение по этому пункту перед сборкой `pg-cluster.json` — от него зависит
структура секции 1. По умолчанию, если не скажете иначе, возьму **вариант A**.
